# ระบบสำรวจ (Expedition) — เวอร์ชัน 1.0.0

นี่คือเสาที่สามของวงจร "จัดทีม–ต่อสู้–ฟาร์ม–evolve": **การฟาร์ม**
กฎทั้งหมดในนี้มีเทสต์รองรับใน `tests/DarkMyst.Expedition.Tests/` และ
`tests/DarkMyst.Content.Tests/ExpeditionContentValidationTests.cs`
โค้ดอยู่ที่ `src/DarkMyst.Expedition/` (ใหม่) และส่วนขยายเล็กน้อยใน `src/DarkMyst.Content/`
กับ `src/DarkMyst.Combat/`

## หลักการ

การสำรวจหนึ่งครั้ง (`ExpeditionRun`) คือแผนที่จุดเชื่อมที่ถูกสร้างขึ้นทั้งหมด **ตั้งแต่ต้น**
จาก seed เดียว ผู้เล่นยืนอยู่ที่จุดหนึ่งเสมอ `AvailableChoices()` บอกว่าไปต่อได้ที่ไหนบ้าง
`Choose(index)` เดินไปยังจุดนั้นและ resolve มันทันที คืนผลว่าเกิดอะไรขึ้น

เหมือน `BattleSimulator` ทุกประการในหลักการ: **เลขจำนวนเต็มล้วน**, ไม่ใช้ `System.Random`
(ใช้ `DeterministicRandom` จาก `DarkMyst.Combat` เสมอ), ลำดับวนซ้ำคงที่ (ไม่มีที่ใดใน
`ExpeditionRun` วนซ้ำ `Dictionary` แล้วให้ผลขึ้นกับลำดับนั้น — น้ำหนักของ `NodeWeights`
อ่านผ่านลำดับคงที่ `{ Battle, Event, Treasure, Rest }` เสมอ) และผลทุกอย่างต้องซ้ำได้จาก
seed เดียวกันตลอดไป

## เนื้อหา (`content/stages.json`)

ไฟล์เดียว มีสามส่วน:

```
stages.json
  rewardTables[]   ตารางสุ่มรางวัล ใช้ร่วมกันได้หลายจุด
  events[]         เหตุการณ์ที่จุด Event สุ่มผลได้
  stages[]         ตัวด่านสำรวจเอง
```

`ContentManifest.Stages` (ค่าเริ่มต้น `"stages.json"`) ชี้ไปยังไฟล์นี้ `ContentPack` โหลดและ
ตรวจสอบมันเหมือนไฟล์อื่นทุกประการ — เพิ่มด่านใหม่ทั้งด่านทำได้ด้วย JSON ล้วน ไม่ต้องแตะโค้ด
ตราบใดที่กลไกที่ใช้มีอยู่แล้ว (นี่คือกฎเดิมของ [05-content-pipeline.md](05-content-pipeline.md)
ที่ใช้กับตัวละครและสกิลอยู่แล้ว)

### `StageData`

| ฟิลด์ | ความหมาย |
| --- | --- |
| `Id`, `Name` | รหัสและชื่อด่าน |
| `RecommendedLevel` | บอกผู้เล่น/ผู้ปรับสมดุลเท่านั้น กฎไม่ได้บังคับจากค่านี้ |
| `Layers` | ชั้นของแผนที่ เรียงจากจุดเริ่มไปหาบอส |
| `BossEncounterId` | ด่านบอสที่จบการสำรวจ — เสมอเป็นจุดเดียวหลังชั้นสุดท้าย ไม่ถูกสุ่มมาแบบจุดทั่วไป |
| `ClearRewardTableId` | รางวัลที่ได้แน่นอนเมื่อชนะบอส |
| `NodeRewardTableId` | รางวัลที่สุ่มได้เมื่อชนะจุด Battle ทั่วไป (ไม่ใช่บอส) — เว้นว่างได้ถ้าอยากให้รางวัลมาจากจุด Treasure เท่านั้น |
| `RestHealPerMille` | สัดส่วนเลือดที่หายไปที่จุด Rest คืนให้ |
| `BranchChancePerMille` | โอกาสต่อจุดที่จะมีทางแยกที่สอง (ดูหัวข้อการสร้างแผนที่) |
| `KeepRewardsOnDefeat` | ดูหัวข้อ "แพ้แล้วเกิดอะไรขึ้น" |

### `StageLayerData`

หนึ่งชั้นของแผนที่ ประกาศ **จำนวนจุด** (`NodeCount`) และ **น้ำหนักของแต่ละชนิดจุด**
(`NodeWeights`, เป็นน้ำหนักเทียบสัดส่วน ไม่ใช่ per-mille — ผลรวมไม่ต้องเป็น 1000)
บวกกับ pool ที่จุดชนิดนั้นสุ่มได้: `EncounterIds` (Battle), `EventIds` (Event),
`TreasureTableId` (Treasure) จุด Rest ไม่ต้องมี pool

`NodeKind.Boss` **ห้ามมีน้ำหนักในชั้นใดเลย** — บอสมีจุดเดียวเสมอ วางหลังชั้นสุดท้าย
ไม่ใช่สิ่งที่สุ่มมา `ContentPack.Validate()` ปฏิเสธชั้นที่ระบุน้ำหนักให้ Boss ทันที

### รางวัลและเหตุการณ์

`RewardTableData` คือรายการ `RewardEntryData` ถ่วงน้ำหนัก (`Gold` / `Material` /
`Character` / `Nothing`) สุ่ม **ครั้งเดียวต่อการเรียกหนึ่งครั้ง** ได้ผลลัพธ์เดียวเสมอ
มี `Nothing` เป็นชนิดหนึ่งโดยตั้งใจ เพื่อให้ปรับอัตราดรอปได้โดยไม่ต้องแกล้งให้ได้อะไรเสมอ

`EventData` คือรายการ `EventOutcomeData` ถ่วงน้ำหนักเช่นกัน ผลที่เป็นไปได้:
`GrantGold`, `GrantMaterial`, `GrantBuffSkill`, `HealTeamPercent`, `Nothing`

## การสร้างแผนที่ (deterministic map generation)

`ExpeditionRun.Start(pack, stageId, seed, leaderSlot, placements)` สร้างแผนที่ทั้งหมด
**ในคราวเดียว** ก่อนผู้เล่นเลือกอะไรเลย ด้วย `DeterministicRandom` สตรีมเดียวที่แยกจาก
การต่อสู้และรางวัลโดยสิ้นเชิง (ดูหัวข้อ seed ด้านล่าง) seed + contentVersion เดียวกัน
ให้แผนที่หน้าตาเดิมทุกประการเสมอ — มีเทสต์ยืนยัน (`The_same_seed_generates_the_identical_map`)

ขั้นตอน ต่อหนึ่งชั้น ตามลำดับ node index คงที่:

1. สุ่มชนิดจุด จากน้ำหนักที่อ่านตามลำดับคงที่ `{ Battle, Event, Treasure, Rest }`
2. สุ่มเลือก id จาก pool ของชนิดนั้น (encounter/event) หรือใช้ `TreasureTableId` ตรง ๆ
   (Treasure ไม่ต้องสุ่มเลือก table เพราะมีตารางเดียวต่อชั้น)

จากนั้นเชื่อมเส้นทางจากชั้นหนึ่งไปอีกชั้น (หรือชั้นสุดท้ายไปหาบอส) ด้วยสามรอบ:

1. **ไปข้างหน้า** — จุดแต่ละจุดในชั้นปัจจุบันได้เส้นทางหลักหนึ่งเส้น กระจายเท่า ๆ กันด้วยการหาร
   จำนวนเต็ม (`next.Start + i * next.Count / current.Count`) ทำให้ **ทุกจุดมีทางไปต่อเสมอ**
2. **ย้อนกลับ** — จุดในชั้นถัดไปที่ยังไม่มีใครชี้มาถึง (เช่นชั้นถัดไปมีจุดเยอะกว่า) ได้เส้นทาง
   เข้ามาหนึ่งเส้น ด้วยสูตรเดียวกันคำนวณย้อนทาง ทำให้ **ทุกจุดมีทางไปถึงเสมอ**
3. **แยกทาง** — แต่ละจุดสุ่ม (ตาม `BranchChancePerMille`) ว่าจะมีเส้นทางที่สองไปจุดข้างเคียงไหม
   นี่คือสิ่งที่ทำให้ "มีทางเลือก" จริง ไม่ใช่เส้นตรงเส้นเดียว

ผลคือ **ไม่มีทางที่ด่านจะสร้างตันตาย** ไม่ว่าผู้เล่นจะเลือกทางไหนก็เดินไปถึงบอสได้เสมอ
(มีเทสต์ `Every_node_has_at_least_one_way_forward_and_every_node_is_reachable` ยืนยันด้วยการ
ไล่ทุกจุดจากจุดเริ่มแบบ BFS) ส่วนที่ป้องกันไม่ให้ชั้นใดชั้นหนึ่ง "สร้างจุดไม่ได้เลย" ทำที่ชั้น
เนื้อหา ไม่ใช่ตอนรัน — ดูหัวข้อการตรวจสอบ

## Seed: ทำไมแต่ละจุดตรวจสอบได้อิสระ

```
runKey        = Mix(seed, Hash(stageId))
mapSeed       = runKey                              (stream แยกสำหรับสร้างแผนที่)
nodeSeed(id)  = Mix(runKey, id + 1)
battleSeed    = nodeSeed(id)                         ส่งเข้า BattleRequest.Seed ตรง ๆ
rewardSeed    = nodeSeed(id) กับ stream แยก (reward)
eventSeed     = nodeSeed(id) กับ stream แยก (event)
```

`Mix` เป็นฟังก์ชันผสมสไตล์ SplitMix64 (`SeedMixer.Mix`) ล้วนเป็นเลข `ulong` ไม่มี
`System.Random` และ `Hash` เป็น FNV-1a 64 บน UTF-8 bytes ของ `stageId` — **ไม่ใช้
`string.GetHashCode()`** เพราะ .NET สุ่มค่านั้นใหม่ทุกโปรเซสโดยตั้งใจ (ป้องกัน hash-flooding
attack) ถ้าใช้ ผลจะต่างกันระหว่างเซิร์ฟเวอร์สองเครื่อง หรือแม้แต่รันเดียวกันสองครั้ง

ผลที่ตามมาซึ่งตั้งใจให้เป็นแบบนี้: **seed ของจุดหนึ่งขึ้นกับ run seed, stage id และ node id
ของมันเท่านั้น ไม่ขึ้นกับว่าผู้เล่นเดินทางไหนมาก่อน** ดังนั้นถ้ามีคนสงสัยผลของการต่อสู้จุดหนึ่ง
กลางการสำรวจ ก็รันซ้ำเฉพาะจุดนั้นได้ทันทีโดยไม่ต้องเล่นทั้งด่านใหม่ — เหมือนกับที่การต่อสู้เดี่ยว
ตรวจสอบได้จาก `BattleRequest` เดี่ยว ๆ ทุกประการ (ดู [02-combat-spec.md](02-combat-spec.md))

การต่อสู้ที่บอสก็ใช้ `BattleSimulator.Run` ตัวเดียวกันเป๊ะ ๆ ไม่มี code path พิเศษ

## HP ติดตัวข้ามจุด (มีเทสต์ `Hp_carries_over_between_battle_nodes`)

**ตัดสินใจ: เลือด "ติดตัว" ข้ามจุดภายในการสำรวจเดียวกัน** — ไม่ฟื้นเต็มทุกครั้งที่เข้าสู้ใหม่
เหตุผล: นี่คือสิ่งที่ทำให้จุด Rest และตัวฮีลมีความหมายจริง และให้ความตึงเครียดที่การฟาร์มควรมี
ถ้าฟื้นเต็มทุกจุด การสำรวจก็แค่การต่อสู้แยกกันหลายครั้งเรียงต่อกัน ไม่ใช่ "การเดินทางหนึ่งครั้ง"

กลไกที่ใช้ทำสิ่งนี้คือ **`UnitDefinition.StartingHp`** ฟิลด์ใหม่ใน `DarkMyst.Combat.Model`
(nullable `int`) `null` = เข้าสู้เต็มเลือดเหมือนเดิมทุกจุดที่เคยมี (ทุก caller เดิมไม่ตั้งค่านี้
เลย จึงไม่มีผลย้อนหลังกับ log การต่อสู้เก่าใด ๆ) ค่า 0 = เข้าสู้ **ล้มไปแล้ว** ตั้งแต่ต้น —
`BattleSimulator.BuildTeam` ตั้ง `Alive = startingHp > 0` แทนที่จะเป็น `true` เสมอ

ผลข้างเคียงที่ตั้งใจปล่อยให้เกิด: หน่วยที่ล้มระหว่างจุดหนึ่งจะ **ยังล้มอยู่** ที่จุดถัดไป จนกว่าจะ
มีสกิล Revive (`OnAllyDown` → `Revive`) ทำงานในการต่อสู้ครั้งต่อไป — **ไม่มีการชุบชีวิตนอกการต่อสู้**
ในเวอร์ชันนี้ จุด Rest ฟื้นเฉพาะหน่วยที่ยังยืนอยู่เท่านั้น (`ExpeditionRun.HealTeam` ข้ามหน่วยที่
`CurrentHp == 0`) นี่เป็นทางเลือกที่ตั้งใจ ไม่ใช่ข้อจำกัดทางเทคนิค: การเสียตัวกลางทางควรมีต้นทุน
ที่ยาวกว่าหนึ่งจุด แต่ก็ไม่ถึงกับจบการสำรวจทั้งชุด

การเพิ่ม `StartingHp` **ไม่ทำให้ `CombatRules.Version` ต้องขยับ** เพราะไม่มี request เก่าใดที่
ตั้งค่านี้มาก่อน (ค่าเริ่มต้น `null` ให้พฤติกรรมเดิมทุกประการ) — ไม่ใช่การเปลี่ยนกฎที่มีอยู่ แต่เป็น
ความสามารถใหม่ที่ query เก่าไม่มีทางแตะถึง

## บัฟเฉพาะรอบ (run-scoped buffs)

จุด Event และ Treasure บางแบบให้บัฟที่มีผล **เฉพาะการสำรวจครั้งนี้** สร้างจากกลไกเดิมล้วน ๆ:
บัฟหนึ่งอันคือ **`SkillDefinition` ที่มีอยู่แล้วใน `skills.json`** โดยมี `Trigger = OnBattleStart`
เมื่อจุดให้บัฟ ระบบแค่เก็บ **skill id** ไว้ใน `ExpeditionRunState.RunBuffSkillIds` — ไม่มีระบบบัฟ
คู่ขนานใด ๆ ถูกสร้างขึ้นเลย

ทุกครั้งที่สร้างทีมสำหรับจุดต่อสู้ถัดไปในรันเดียวกัน (`ExpeditionRun.BuildBattleTeam`) สกิลบัฟ
ทุกอันที่สะสมไว้จะถูก **เติมเข้าไปในรายการสกิลของหน่วยทุกตัว** (ไม่ใช่แค่ผู้นำ) เหตุผลที่เติมให้
ทุกตัวแทนที่จะติดไว้ที่ผู้นำตัวเดียว: `OnBattleStart` ของหน่วยที่ล้มไปแล้วจะไม่ยิง (ดู
[02-combat-spec.md](02-combat-spec.md)) ถ้าผู้นำล้มไปจากจุดก่อนหน้าและบัฟติดอยู่ที่ผู้นำเพียง
คนเดียว บัฟทั้งก้อนจะหายไปเงียบ ๆ ทั้งที่ผู้เล่นไม่ได้ทำอะไรผิด — ความประหลาดใจแบบนี้ไม่คุ้ม
เติมให้ทุกตัวแล้วใช้ `StackRule.Ignore` แทน: ตัวแรกที่ยังยืนอยู่ตอน `OnBattleStart` เป็นคนใช้บัฟ
ที่เหลือถูกมองข้ามเงียบ ๆ (ไม่ใช่ error) ผลลัพธ์เดียวกันไม่ว่าใครจะยืนอยู่กี่คน

**ทำไมถึงหยุดมีผลทันทีที่จบรัน:** `RunBuffSkillIds` อยู่ใน `ExpeditionRunState` เท่านั้น
ไม่เคยถูกเขียนกลับไปที่ `OwnedCharacter` หรือ `characters.json` เลยแม้แต่บรรทัดเดียว
เมื่อรันจบ (ชนะหรือแพ้) และไม่มีใคร resume มันอีก state ทั้งก้อนก็แค่ถูกทิ้ง — บัฟไม่ได้ถูก "ถอด"
ทีหลัง มันไม่เคยมีที่ให้ "อยู่ต่อ" ตั้งแต่แรก มีเทสต์ยืนยันสามชั้น
(`A_run_scoped_buff_does_not_survive_the_run_it_was_granted_in`): รันใหม่ไม่เห็นบัฟ,
`RunBuffSkillIds` ของรันใหม่ว่างเปล่า, และ `CharacterData.SkillIds` ของตัวละครต้นแบบไม่เคย
ถูกแก้เลย

`ContentPack.Validate()` ปฏิเสธสกิลที่ประกาศเป็น `GrantBuffSkill` แต่ trigger ไม่ใช่
`OnBattleStart` (จะไม่มีทางทำงาน) หรือติด `IsLeaderSkill` (จะกลับไปมีปัญหาแบบผู้นำล้มแล้ว
บัฟหายที่อธิบายไว้ข้างบนอีกครั้ง)

## แพ้แล้วเกิดอะไรขึ้น

แพ้ที่จุด Battle หรือบอส (รวมถึงเสมอ — [02-combat-spec.md](02-combat-spec.md) กำหนดให้เสมอ
นับเป็นแพ้ฝั่งบุกใน PvE เสมอ) **จบการสำรวจทันที** `AvailableChoices()` คืนรายการว่างเปล่า
หลังจากนั้น และเรียก `Choose` ซ้ำจะโดนปฏิเสธด้วย `ExpeditionException`

**ตัดสินใจ: ของรางวัลที่สะสมไว้ก่อนแพ้ ถูกเก็บไว้โดยค่าเริ่มต้น** (`StageData.KeepRewardsOnDefeat
= true`) เหตุผล: การเสียของทั้งหมดจากการแพ้ไฟต์เดียวหลังเดินมาหลายจุด คือสิ่งที่ทำให้คนเลิกฟาร์ม
— ไม่ใช่ทำให้กลับไปฟาร์มต่อ ซึ่งขัดกับเป้าหมายทั้งของระบบนี้และของ vertical slice ตาม
[06-roadmap.md](06-roadmap.md) แต่ก็เปิดให้ดีไซเนอร์ตั้งด่านที่โหดกว่านั้นได้ ถ้าอยากให้ด่านใด
ด่านหนึ่ง "ทุ่มหมดหน้าตัก" จริง ๆ ก็ตั้ง `keepRewardsOnDefeat: false` ในเนื้อหาได้ — เป็นข้อมูล
ไม่ใช่โค้ด (มีเทสต์ทั้งสองพฤติกรรม)

## จบด่านสำเร็จ

ชนะบอส → `RunStatus.Cleared`, รางวัลจาก `ClearRewardTableId` สุ่มครั้งเดียวรับประกัน (ไม่มี
`Nothing` เป็นทางเลือกก็ได้ ถ้าอยากให้ชนะบอสได้อะไรเสมอ) `AvailableChoices()` คืนว่างเปล่า
เหมือนกรณีแพ้ — ทั้งสองสถานะ ทั้ง `Cleared` และ `Failed`, ปิดรันไม่ให้เดินต่อ

## การล็อกทีมและเวอร์ชัน

`ExpeditionRun.Start` **คัดลอกค่าของทีม (เลเวล, focus, สแตทที่สืบทอด) ไว้ใน
`ExpeditionRunState.Team` ตั้งแต่ต้น** ไม่อ่านค่าจากบัญชีผู้เล่นซ้ำระหว่างเล่น เหตุผลเดียวกับที่
`OwnedCharacter.ContentVersion` ต้องปักไว้ ([03-evolve-spec.md](03-evolve-spec.md) ข้อ 5):
การเลเวลอัพหรือ evolve ตัวละครตัวเดียวกันที่บ้าน **ระหว่าง** ที่การสำรวจกำลังค้างอยู่ ต้องไม่มีผล
กับการสู้ที่กำลังเล่นอยู่กลางด่าน — มิเช่นนั้นผู้เล่นจะเจอสแตทเปลี่ยนกลางทางโดยไม่มีใครบอก

`ExpeditionRunState` ปัก `ContentVersion` และ `RulesVersion` ไว้เหมือนกัน `Resume(pack, json)`
และแม้แต่ `Choose(pack, index)` ธรรมดา **ปฏิเสธทันทีถ้า `pack` ที่ส่งมาคนละเวอร์ชันกับตอนเริ่ม**
นี่คือกฎเดียวกับที่ [05-content-pipeline.md](05-content-pipeline.md) กำหนดไว้สำหรับการสำรวจ
โดยเฉพาะ: **"การสำรวจที่กำลังเล่นค้างอยู่ต้องจบด้วยเวอร์ชันที่เริ่ม"** มีเทสต์ยืนยันทั้งการ resume
ข้ามเวอร์ชัน content และการปลอมแปลง `rulesVersion` ใน JSON ที่บันทึกไว้

## Serialization

`ExpeditionRunState` เป็นข้อมูลล้วนทั้งก้อน — ไม่มี live RNG, ไม่มี `ContentPack`, ไม่มี
`BattleSimulator` ค้างอยู่ในตัวมันเลย จึง serialize ด้วย `ContentPack.SerializerSettings`
(camelCase, string enum) ตัวเดียวกับที่ content pack ใช้ได้ตรง ๆ `ExpeditionRun.Serialize()` /
`ExpeditionRun.Resume(pack, json)` คือคู่ save/load เซิร์ฟเวอร์เก็บ JSON นี้ไว้แทนตัวแปรในหน่วยความจำ
ได้เลย มีเทสต์ round-trip เต็มรูปแบบ: เล่นครึ่งทาง → serialize → resume → เล่นต่อจนจบ →
เทียบ checksum, สถานะ, และของรางวัลสะสม กับรันที่เล่นรวดเดียวไม่มีการ serialize เลย — ต้องตรงกัน
เป๊ะ

`ExpeditionLogEntry` (ที่เก็บอยู่ใน state) **ไม่เก็บ log เหตุการณ์เต็มของการต่อสู้** เก็บแค่
checksum, RngCalls, และผลแพ้ชนะ — ส่วนนี้ต่างจาก `ExpeditionNodeOutcome` (ค่าที่ `Choose` คืนสด
ๆ ตอนเรียก) ซึ่งมี `BattleResult` เต็มรูปแบบให้ทันที เหตุผล: log เต็มของทุกไฟต์ตลอดทั้งด่านจะทำให้
save โตขึ้นเรื่อย ๆ โดยไม่จำเป็น เพราะ log เต็มของจุดใดจุดหนึ่งคำนวณใหม่ได้เสมอจาก
`(seed, stageId, nodeId)` ตามที่อธิบายไว้ในหัวข้อ seed — เก็บ checksum ไว้พอสำหรับ "ทั้งสองฝั่ง
เห็นตรงกันไหม" เหมือนที่ `BattleResult.Checksum` ทำ

`ExpeditionRunState.ComputeChecksum()` ใช้สูตร FNV-1a 64 เดียวกับ `BattleResult`
เพื่อสรุปทั้งรันเป็นสตริงเดียว เทียบกันได้ทันทีว่าสองรันเห็นตรงกันทุกจุดหรือไม่ และ
`TotalRngCalls` สะสมจำนวนครั้งสุ่มของทั้งการสร้างแผนที่ การต่อสู้ทุกจุด และการสุ่มรางวัล/
เหตุการณ์ทุกจุด — เป็นตัวจับความเพี้ยนระดับรัน เหมือนที่ `RngCalls` จับระดับการต่อสู้เดี่ยว

## การตรวจสอบ (`ContentPack.Validate()`)

ส่วนขยายที่เพิ่มเข้าไปตรวจ:

- ทุก `encounterId` / `eventId` / `treasureTableId` / `bossEncounterId` /
  `clearRewardTableId` / `nodeRewardTableId` ที่ stage อ้างถึง ต้องมีอยู่จริง
- ชั้นที่ระบุน้ำหนักให้ชนิดจุดใด ต้องมี pool ของชนิดนั้นไม่ว่างเปล่า (Battle ต้องมี
  `encounterIds`, Event ต้องมี `eventIds`, Treasure ต้องมี `treasureTableId`)
- **ชั้นที่ผลรวมน้ำหนักเป็นศูนย์ถูกปฏิเสธ** — นี่คือ "ชั้นที่สร้างจุดไม่ได้เลย" ตามที่โจทย์กำหนด
  จับได้ตอนโหลด ไม่ใช่ตอนรัน
- `NodeKind.Boss` ห้ามมีน้ำหนักในชั้นใดเลย
- ตารางรางวัลและเหตุการณ์ ต้องมีอย่างน้อยหนึ่งตัวเลือกที่น้ำหนักเป็นบวก, รางวัลชนิด `Character`
  ต้องอ้างถึงตัวละครที่มีจริง, `minAmount` ต้องไม่เกิน `maxAmount`
- `GrantBuffSkill` ต้องอ้างสกิลที่มีจริง เป็น `OnBattleStart` และไม่ใช่ `IsLeaderSkill`
  (เหตุผลอยู่ในหัวข้อบัฟเฉพาะรอบด้านบน)
- `rulesVersion` ของ content ต้องตรงกับ `CombatRules.Version` (กฎเดิมของ pack ทั้งก้อน
  ใช้ร่วมกับส่วนนี้)

ตรวจได้จากบรรทัดคำสั่งเดิม:

```bash
dotnet run --project tools/DarkMyst.SimRunner -- validate
```

ๆ ไม่ใช่จากไหวพริบของผู้เล่นจำลอง — นี่คือสิ่งที่ต้องการเวลาวัดเส้นความยาก ไม่ใช่กลยุทธ์ที่ดีที่สุด

### เส้นความยากที่วัดได้ (ด่าน `stg_ashfields`, 300 seed ต่อระดับ)

| เลเวลทีม | อัตราจบด่าน | จุดเฉลี่ยที่ผ่าน | ทองเฉลี่ยต่อรัน |
| --- | --- | --- | --- |
| 4 | 0.0% | 3.1 | 48.8 |

| 12 (recommended) | 57.0% | 4.0 | 182.7 |
| 16 | 99.7% | 4.0 | 281.1 |
| 20+ | 100.0% | 4.0 | 281.1 |

ด่านเปิดใกล้เคียงกับ `recommendedLevel` ที่ตั้งไว้ (12) พอดี และมีทั้งช่วงที่แพ้เกือบตลอด (lv4-8)
กับช่วงที่ชนะเกือบตลอด (lv16+) — เส้นโค้งจริง ไม่ใช่ 0% หรือ 100% ตลอดทุกระดับ

มักไปตายที่บอสพอดี ไม่ใช่ตายกลางทาง เพราะจุด Battle ทั่วไปในด่านนี้ยังใช้ด่านที่ปรับสมดุลไว้แล้ว

## สิ่งที่ยังไม่ทำและขอบเขตที่ตั้งใจตัดออก

- **ไม่มีการชุบชีวิตนอกการต่อสู้** — อธิบายไว้แล้วข้างบน เป็นทางเลือกโดยตั้งใจ ไม่ใช่งานที่ยังไม่เสร็จ
- **เหตุการณ์ไม่มีผลลบต่อทีม** (`EventOutcomeKind` มีแต่ผลบวกหรือว่างเปล่า) — เพื่อไม่ให้เกิดคำถาม
  ว่า "เหตุการณ์ฆ่าทีมได้ไหม แล้วนับเป็นแพ้รันหรือเปล่า" ซึ่งยังไม่มีเวลาตอบให้ครบในรอบนี้
  ถ้าต้องการในอนาคต ควรเพิ่มเป็น `EventOutcomeKind` ใหม่พร้อมกฎที่ชัดเจนแยกต่างหาก
- **ทีมล็อกที่ตอนเริ่มรัน สลับตัวกลางทางไม่ได้** — ตามที่อธิบายในหัวข้อการล็อกทีม

## ข้อจำกัดที่ทราบอยู่แล้ว (known limitations)

**`ExpeditionRun.Choose` ไม่ได้ทำแบบธุรกรรม (transactional)** ระหว่าง resolve จุดหนึ่งจุด
โค้ดจะแก้ `State` ไปเรื่อย ๆ (HP ที่ติดตัว, `RunBuffSkillIds`, ของสะสม, `Status`) ก่อนที่จะเขียน
`ExpeditionLogEntry` ปิดท้าย ถ้าเนื้อหาที่ผ่าน `ContentPack.Validate()` แล้วดันอ้างถึง id ที่หายไป
ระหว่างทาง (ซึ่งไม่ควรเกิดขึ้นได้เลยถ้าโหลดผ่านการตรวจสอบ) หรือมี exception อื่นใดโผล่ขึ้นมากลาง
การ resolve การเรียกครั้งนั้นอาจทิ้ง `State.CurrentNodeId` ไว้ที่จุดใหม่ทั้งที่ log ของจุดนั้นยังไม่ถูก
บันทึก — เป็นสถานะค้างที่ไม่สอดคล้องกันเอง (`State.CurrentNodeId` ขยับแล้วแต่ `State.Log` ไม่มี
รายการของมัน)

นี่เป็นความเสี่ยงที่ยอมรับไว้ในรอบนี้ ไม่ใช่สิ่งที่ถูกมองข้าม เพราะเป็น path ที่เนื้อหาซึ่งผ่านการ
ตรวจสอบแล้วไม่ควรไปถึงได้ **เมื่อสร้างเซิร์ฟเวอร์จริงในระยะ D** ที่ต้องเก็บ `ExpeditionRunState`
ลงฐานข้อมูล ทางแก้ที่ถูกต้องคือ: เซิร์ฟเวอร์ต้อง resolve จุดหนึ่งจุดลงใน **สำเนาชั่วคราวของ state**
(clone แล้วเรียก `Choose` บนสำเนานั้น หรือเทียบเท่า) และ **commit ทับ state จริงก็ต่อเมื่อจุดนั้น
resolve จบสมบูรณ์แล้วเท่านั้น** — วิธีเดียวกับที่ [03-evolve-spec.md](03-evolve-spec.md) กำหนดให้
evolve ต้องหักวัตถุดิบ "ในธุรกรรมเดียว" ไม่ใช่ทีละขั้น `ExpeditionRun` เองไม่ได้ทำสิ่งนี้ให้ เพราะ
ไม่รู้จักฐานข้อมูลหรือธุรกรรมของเซิร์ฟเวอร์เลย — เป็นหน้าที่ของชั้นที่เรียกใช้มัน

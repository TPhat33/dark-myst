# ระบบสุ่มตัวละคร แผนปล่อยเนื้อหา และ telemetry ของตัวละคร

> **สถานะ: โครงสร้างล็อกได้ อัตรายังล็อกไม่ได้**
> กลไกทุกอย่างในเอกสารนี้ตัดสินใจแล้วและเขียนเป็นกรณีทดสอบได้ แต่ **ตัวเลขอัตราการออก
> และรายได้ต่อวันยังล็อกไม่ได้** จนกว่าจะมีข้อมูลการฟาร์มจริงจากระยะ C ด้วยเหตุผลเดียวกับที่
> [04-economy-spec.md](04-economy-spec.md) ระบุไว้ — คำถาม "60 ครั้งใช้เวลากี่วันถ้าเล่นฟรี"
> ตอบไม่ได้ถ้ายังไม่รู้ว่าฟาร์มได้เท่าไรต่อชั่วโมง

## หลักการเดียวที่ทุกอย่างในเอกสารนี้ตามมา

> **การสุ่มให้ "สิทธิ์เข้าถึงสายตัวละคร" — บันได evolve ให้ "พลัง"**

กลไกนี้**บังคับอยู่แล้วโดยไม่ต้องเพิ่มกฎใหม่** เพราะ `progression.json` ผูกเพดานเลเวลไว้กับ
**ขั้น evolve ไม่ใช่ rarity**:

```
maxLevelByStage = [20, 40, 60]
```

ตัวละครที่ขั้น 1 ตันที่เลเวล 20 เสมอ ไม่ว่าจะหายากแค่ไหน เทียบให้เห็นภาพ (ตัวเลขจาก
`content/characters.json` ปัจจุบัน):

| | Ashen Revenant Lord (ปั้นจากขั้น 1 ถึงขั้น 3) | ตัวที่เพิ่งสุ่มได้ ขั้น 1 |
| --- | --- | --- |
| เพดานเลเวล | 60 | **20** |
| HP ที่เพดาน | ~10,600 (รวม inherited 300‰) | ~3,100 |
| Attack ที่เพดาน | ~1,040 | ~330 |

ต่างกันราวสามเท่า **สิ่งที่ซื้อด้วยการสุ่มจึงไม่ใช่พลัง แต่คือการได้รู้จักตัวละครตัวนั้น**
และนั่นคือสิ่งที่รักษาจุดขายข้อ 2 ของเกม (*"งานปั้นที่มีคุณค่า"* — ดู
[00-overview.md](00-overview.md)) ไว้ได้ ถ้าซื้อข้ามบันไดได้เมื่อไร จุดขายนั้นหายทันที

**ผลที่ตามมาที่ต้องยอมรับ:** ตัวที่สุ่มได้ใหม่จะอ่อนกว่าตัวที่ปั้นมานานเสมอในช่วงแรก
นี่เป็นความตั้งใจ ไม่ใช่บั๊ก UI ต้องสื่อสารเรื่องนี้ให้ชัดตอนผู้เล่นเปิดได้ตัวใหม่ ไม่งั้น
ผู้เล่นจะรู้สึกว่า "เปิดได้ของหายากแต่มันอ่อน" ซึ่งเป็นความรู้สึกที่ทำลายระบบสุ่มได้เร็วที่สุด

## โครงชั้นความหายาก

ชั้นอิงกับ `rarity` ที่มีอยู่แล้วใน `characters.json` **สุ่มได้เฉพาะร่างขั้น 1 เท่านั้น** —
ขั้น 2 และ 3 มาจากการ evolve ทางเดียว ซึ่งเป็นสิ่งที่ทำให้หลักการข้างบนเป็นจริง

| ชั้น | อัตรารวมที่เสนอ | หมายเหตุ |
| --- | --- | --- |
| R5 (Legendary) | 1.0% | สุ่มได้ทางเดียว ดูหัวข้อ Legendary |
| R4 | 3.0% | |
| R3 | 36% | |
| R2 | 60% | |

**ณ content 0.4.0 ยังไม่มีสาย R5 ที่สุ่มได้เลย** — rarity 5 มีอยู่ร่างเดียวคือ Ashen Revenant
Lord ซึ่งเป็นขั้น 3 ที่ไปถึงได้ด้วยการ evolve เท่านั้น ชั้นบนสุดที่สุ่มได้จริงตอนนี้คือ R4
(2 สาย 2 บทบาท หลังการรีบาลานซ์ — ดู [07-testing-plan.md](07-testing-plan.md) หัวข้อ
"องค์ประกอบโรสเตอร์") แถว R5 ในตารางข้างบนจึงเป็นโครงที่รอสายแรกเข้ามา

**องค์ประกอบของโรสเตอร์ปัจจุบันดูได้จาก `simrunner roster`** ไม่ใช่จากตารางในเอกสารนี้ —
ตารางที่เขียนมือจะล้าสมัยภายในสองรอบอัปเดตเนื้อหา แล้วกลายเป็นข้อมูลผิดที่คนเชื่อ
ซึ่งแย่กว่าไม่มีเลย เครื่องมือนั้นอ่านจาก `content/` สด ๆ และมีเทสต์บังคับขอบเขตสมดุลไว้ด้วย

## การันตีสามชั้น — ทุกชั้นต้องมองเห็นได้บนหน้าจอ

| กลไก | ค่าที่เสนอ | เหตุผล |
| --- | --- | --- |
| พื้นทุก 10 ครั้ง | ได้ R3 ขึ้นไปอย่างน้อย 1 | กันความรู้สึก "เปิดสิบครั้งได้ขยะสิบครั้ง" |
| soft pity | จากครั้งที่ 40 เพิ่มโอกาส R4+ 2.5pp ต่อครั้ง | **นี่คือส่วนที่สร้างความลุ้น** |
| hard pity | ครั้งที่ 60 ได้ R4+ แน่นอน | ล็อกกรณีแย่ที่สุด |
| Spark | สะสม 150 ครั้ง แลกสายไหนก็ได้ รวม Legendary | ผู้เล่นรู้เพดานตั้งแต่วันแรก |

**ตัวนับ pity ต้องแสดงบนหน้าจอเสมอ** — pity ที่ซ่อนไว้สร้างความกังวล pity ที่เห็นสร้าง
ความคาดหวัง นี่เป็นความต่างที่สำคัญที่สุดข้อเดียวระหว่างระบบสุ่มที่สนุกกับที่น่าอึดอัด

pity และ spark **สะสมข้ามเซสชันและข้ามเครื่อง** จึงต้องเก็บฝั่งเซิร์ฟเวอร์ ไม่ใช่บนอุปกรณ์

## ตัวซ้ำต้องไม่มีวันเป็นของเหลือ

นี่คือหัวใจที่เชื่อมระบบสุ่มเข้ากับ evolve

ปัญหาที่ต้องแก้: `inheritedBonusPerMille` สะสมได้ถึงเพดาน 300‰ แต่ **เพิ่มได้เฉพาะตอน evolve
เท่านั้น** ถ้าผู้เล่นไต่ I→II→III ด้วยวัตถุดิบอ่อนแล้วจบที่ 80‰ ตัวละครตัวนั้น**ด้อยกว่า
ตัวเดียวกันที่คนอื่นปั้นถึง 300‰ อย่างถาวร โดยไม่มีทางไล่ตาม** — และวิธีเดียวที่เหลือคือทิ้ง
ตัวที่ผูกพันแล้วไปเริ่มใหม่ ซึ่งขัดกับจุดขายข้อ 1 ของเกมโดยตรง

**ทางแก้: Echo shard + Attune**

```
สุ่มได้สายที่มีอยู่แล้ว
  → ได้ OwnedCharacter ตัวที่สองจริง ๆ (ใช้เป็นวัตถุดิบสายเดียวกัน 100%)
  → และได้ Echo shard ของสายนั้น

Echo shard + ทอง → Attune → inheritedBonusPerMille ไต่ขึ้น จนถึงเพดาน 300‰
```

| ชั้นของตัวที่ซ้ำ | Echo shard ที่ได้ |
| --- | --- |
| R2 | 5 |
| R3 | 10 |
| R4 | 20 |
| R5 | 40 |

อัตราที่เสนอ: **4 shard = 1‰** เพดานยังเป็น 300‰ เท่าเดิม `Attune` ขึ้นได้อย่างเดียว
ไม่มีทางลง จึงไม่ต้องมีปุ่มยกเลิก

ผลที่ได้คือ **การเปิดซ้ำกลายเป็นคำตอบของปัญหา "ปั้นพลาด" พอดี** ผู้เล่นที่ปั้นพลาดไม่ต้อง
เริ่มใหม่ แค่เล่นต่อกับตัวเดิมแล้วมันจะดีขึ้น

หมายเหตุ: การเลือก focus ผิด (Offense ทั้งที่อยากได้ Guard) **แก้ได้อยู่แล้ว**ด้วย Reforge
Stone ตาม [03-evolve-spec.md](03-evolve-spec.md) — `Attune` แก้คนละปัญหากัน

## Legendary

**ตั้งใจให้มีตัวเดียวก่อน** แล้วค่อยเพิ่มทีละตัว การมีตัวละครครบตั้งแต่วันแรกทำให้ไม่เหลือ
อะไรไว้ดึงผู้เล่นให้อยู่ต่อ

คุณสมบัติ:

- สุ่มได้ทางเดียว ไม่มีในตารางรางวัลของการสำรวจ ไม่มีในร้าน (แลกด้วย spark ได้)
- เริ่มที่ขั้น 1 เหมือนทุกสาย และต้องไต่บันได evolve เหมือนกัน
- rarity มีผลกับ base stat และชุดสกิล **ไม่ใช่การข้ามบันได**

### กับดักที่ต้องแก้พร้อมกัน

[03-evolve-spec.md](03-evolve-spec.md) กำหนดว่าขั้น **II → III ต้องมีวัตถุดิบสายเดียวกัน
อย่างน้อย 1 ตัว** สำหรับ Legendary ที่สุ่มได้ทางเดียว นั่นแปลว่า **ต้องสุ่มตัวเดิมซ้ำที่
อัตรา 1%** ซึ่งเป็นความโหดระดับที่คนเลิกเล่น

**ทางแก้: ไอเทม `Myst Effigy`** แลกด้วย spark token ใช้แทนวัตถุดิบสายเดียวกันได้ 1 ตัว

เลือกทางนี้แทนการยกเว้นกฎ same-line ให้ Legendary เพราะ (ก) ไม่ต้องแก้กฎ evolve ที่ล็อกและ
เขียนเป็นเทสต์ไปแล้ว และ (ข) เพดานความโหดยังคำนวณเป็นจำนวนครั้งที่สุ่มได้ ซึ่งเป็นสิ่งที่
ผู้เล่นวางแผนได้

## แผนปล่อยตัวละคร

ตอนนี้ทั้ง 14 สายเปิดหมดแล้ว ถ้าอยากทยอยปล่อยจริง **ต้องกันไว้ตั้งแต่ตอนเปิดตัว**

| ช่วง | ทำอะไร |
| --- | --- |
| เปิดตัว | เปิด ~10 สาย เก็บที่เหลือไว้ |
| ทุก 3 สัปดาห์ | ปล่อย 1 สาย สลับระหว่าง "อุดช่องว่าง" กับ "ตัวชูโรง" |
| ทุกไตรมาส | ทบทวน telemetry แล้วปรับสมดุล (ดูหัวข้อถัดไป) |

**เงื่อนไขบังคับของทุกสายใหม่: ต้องระบุได้ว่าอุดช่องไหน** ในผลของ `simrunner roster`
ถ้าตอบไม่ได้ว่าธาตุไหน บทบาทไหน หรือแมตช์อัพไหนที่มันเติมเต็ม ก็ยังไม่ควรเพิ่ม —
เทสต์สมดุลจะปฏิเสธเองอยู่แล้วถ้ามันทำให้โรสเตอร์เบ้

## Telemetry ระดับตัวละคร

ต่อยอดจากหลักการใน [08-metrics.md](08-metrics.md) — **เก็บเหตุการณ์ อย่าเก็บตัวเลขสรุป**
และติด `contentVersion` กับ `rulesVersion` ไปกับทุกเหตุการณ์ ไม่งั้นเทียบก่อน/หลังปรับสมดุล
ไม่ได้เลย

| เก็บอะไร | ตอบคำถามอะไร |
| --- | --- |
| อัตราการถูกเลือกลงทีม ต่อสาย ต่อด่าน | ตัวไหนคนนิยม |
| อัตราชนะเมื่อมีตัวนั้นในทีม เทียบกับเมื่อไม่มี | ตัวไหนแรงจริง |
| อัตราการ evolve สำเร็จ ต่อสาย | ตัวไหนคนยอมลงทุนปั้น |
| สายแรกที่ผู้เล่นเลือก evolve | อะไรคือตัวโปรดจริง ๆ |
| ถูกดองหลังได้มา N วัน | ตัวไหนน่าตื่นเต้นตอนเปิดได้ แต่ไม่มีที่ใช้ |
| ครั้งที่สุ่มก่อนได้ R4/R5 ตัวแรก | pity ทำงานตามที่ออกแบบไหม |

### กรอบวิเคราะห์: ความนิยม × ความแรง

เอาความนิยมจาก telemetry ไปวางคู่กับความแรงที่วัดได้ offline จาก `simrunner matrix`

| | แรงจริง | ไม่แรง |
| --- | --- | --- |
| **นิยมสูง** | ปกติ ไม่ต้องทำอะไร | **กับดัก** — ผู้เล่นเข้าใจผิด แก้ด้วยการสื่อสาร/UI **ไม่ใช่บัฟ** |
| **นิยมต่ำ** | **เพชรในตม** — แก้ด้วยการทำให้มองเห็น **ไม่ใช่บัฟ** | ต้องบัฟจริง |

สองช่องกลางคือเหตุผลที่ต้องมีข้อมูลทั้งสองด้าน **ถ้ามีแต่ตัวเลขความนิยมจะบัฟผิดตัว** —
จะไปบัฟตัวที่แรงอยู่แล้วแต่ไม่มีคนรู้ และปล่อยตัวที่คนแห่ใช้ทั้งที่มันไม่คุ้มไว้เฉย ๆ

## การตัดสินใจเรื่องการขาย — ตัดสินแล้ว (2026-09-23)

เดิม [04-economy-spec.md](04-economy-spec.md) ห้ามขายการสุ่มโดยปริยาย (*"อัญมณีซื้อเวลาและ
ความสะดวก ไม่ใช่สแตท"*) มีสองทางให้เลือก: แก้กฎ หรือให้สุ่มด้วยสกุลเงินฟรีอย่างเดียว

**เจ้าของโปรเจกต์เลือกทางแรก — ขายการสุ่ม** เพราะเป็นช่องทางรายได้ที่ขาดไม่ได้ กฎใน 04
แก้เป็น *"อัญมณีซื้อโอกาสและเวลา ไม่เคยซื้อความได้เปรียบที่การันตี"* แล้ว ทางนี้ยังเข้ากับ
หลักการข้อแรกของเอกสารนี้ (สุ่มได้แค่สิทธิ์เข้าถึง พลังยังต้องปั้นเอง) และ spark ที่เป็นเพดาน
เวลา ไม่ใช่เพดานพลัง

ก่อนเปิดจริงต้อง **เปิดเผยอัตราการออก** ตามข้อกำหนดของ store (ดู
[04-economy-spec.md](04-economy-spec.md))

### R5 — มาทีหลัง

ตัดสินแล้วว่า **ยังไม่สร้างสาย R5 ตอนนี้** แถว R5 ในตารางอัตราคงไว้เป็นโครง ระหว่างนี้โรล
ที่ตกชั้น R5 จะพับลงเป็น R4 (และ `simrunner summon` เตือนทุกครั้ง) เมื่อสาย R5 แรกเข้ามา
ให้วัดใหม่ด้วยสายจริงแทน `--hypothetical-r5`

### อ้างอิงเกมอื่น — วัด อย่าลอก

เจ้าของโปรเจกต์ขอให้ดูเกมที่มีระบบสุ่มเป็นที่ยอมรับ เช่น Genshin Impact และ Ragnarok แล้ว
ปรับมาใช้ หลักที่ใช้: **เอาโครงมาเทียบด้วยเครื่องมือเดียวกัน แล้วตัดสินจากตัวเลข** ไม่ใช่
ลอกอัตรามาทั้งชุด เพราะ Genshin ออกแบบอัตราให้เข้ากับรายได้ต่อวันของเกมนั้น ซึ่งไม่ใช่ของเรา

**Genshin Impact** (ข้อมูลสาธารณะ): ชั้นบนสุด 0.6% เริ่ม soft pity ที่ครั้งที่ 74 (+6% ต่อครั้ง)
hard pity ที่ 90 อัตรารวมเฉลี่ยราว 1.6% ต่อครั้ง ชั้นรอง 5.1% การันตีทุก 10 ครั้ง และ pity
สองชั้น **แยกกัน** ตัวซ้ำกลายเป็น constellation ซึ่งตรงกับแนว Echo shard ของเรา

**Ragnarok** ไม่มีโครง pity ที่เปิดเผยเป็นมาตรฐานให้เทียบเชิงตัวเลข บทเรียนที่ใช้ได้คือด้านกลับ:
การสุ่มอัตราต่ำโดยไม่มีเพดานคือสิ่งที่ทำให้ระบบถูกมองว่าเอาเปรียบ — ซึ่งเรากันไว้แล้วด้วย
hard pity และ spark ที่แสดงบนจอ

`simrunner summon --rules genshin-like` และ `--compare` จำลองโครงแบบ Genshin บนโรสเตอร์ของเรา
เพื่อให้เทียบได้ตรง ๆ — ผลการเทียบอยู่ในหัวข้อ "วิธีวัด"

## สิ่งที่ต้องมีก่อนล็อกตัวเลข

**เพิ่มเข้ามา 2026-09-24: endpoint สุ่มจริงมีแล้ว** (`POST /summon/pull`,
`/summon/spark-redeem`, `/summon/attune`, `GET /summon/state` — ดู
[10-backend-spec.md](10-backend-spec.md) หัวข้อ "Summon") กฎที่ endpoint นี้ใช้ยังเป็น
`SummonRules.Proposed` ตัวเดิม ยังไม่ได้ล็อก และราคาสกุลเงิน
(`SummonService.PullPriceGemsPerPull`) เป็นค่าที่ตั้งไว้ชั่วคราวเท่านั้น (ติด `NOT LOCKED` ใน
โค้ด) — สิ่งที่เปลี่ยนคือตอนนี้มีทางเก็บตัวเลขฟาร์มจริงจากระยะ C ผ่าน `summon_pulled` +
`attune_completed` telemetry แล้ว (ก่อนหน้านี้มีแต่ `simrunner summon` ซึ่งเป็นการจำลอง ไม่ใช่ข้อมูล
ผู้เล่นจริง) รายการข้อ 1-4 ด้านล่างยังตอบไม่ได้จนกว่าจะมีผู้เล่นจริงเล่นผ่าน endpoint นี้พอจะวัดได้

จากระยะ C:

1. ผู้เล่นฟรีได้สิทธิ์สุ่มกี่ครั้งต่อวัน
2. เวลาเฉลี่ยจนได้ R4 ตัวแรก และจนถึง spark
3. เวลาเฉลี่ยจน Attune สายหนึ่งเต็มเพดาน 300‰
4. สัดส่วนเวลาที่ลดลงถ้าจ่ายเงิน

### วิธีวัด

`simrunner summon` — จำลองผู้เล่น N คน (ค่าเริ่มต้น 10,000 คน สุ่มไม่เกิน 300 ครั้งต่อคน)
รายงานการกระจายของ:

- จำนวนครั้งจนได้ R4+ ตัวแรก, R4 ตัวแรก และ R5 ตัวแรก (mean, median, p90, worst)
- จำนวนครั้งจนได้สายที่ระบุตัวแรก สำหรับทุกสาย R4 (และ R5 ถ้ามี) พร้อมสัดส่วนผู้เล่นที่ยัง
  ไม่ได้สายนั้นตอนถึง spark (150 ครั้ง) — นี่คือกลุ่มที่ spark เป็นตัวส่งสายนั้นให้จริง ๆ
- อัตราการได้ตัวซ้ำ ต่อสายและต่อชั้น
- จำนวนครั้งจนสะสม Echo shard พอ Attune หนึ่งสายเต็มเพดาน 300‰ — ใช้งบ pull แยกต่างหาก
  (`--attune-max-pulls`, ค่าเริ่มต้น 5,000) เพราะเต็มเพดานมักใช้ครั้งมากกว่างบเล่นจริงมาก

วิธีเดียวกับที่ใช้พิสูจน์สมดุลทีมและเส้นความยากมาแล้ว — **ตัวเลขทุกตัวในเอกสารนี้ต้อง
ทำซ้ำได้ด้วยคำสั่ง ไม่ใช่มาจากความรู้สึก** รันซ้ำด้วย seed เดิมได้ผลเดียวกันทุกไบต์
(`DeterministicRandom` เท่านั้น ไม่มี `System.Random`)

ที่ content 0.4.0 ยังไม่มีสาย R5 ที่สุ่มได้ (ดูหัวข้อ "โครงชั้นความหายาก") เครื่องมือจึงมี
`--hypothetical-r5 N` เพิ่มสาย R5 สมมติ N สายเข้าไปในพูล เพื่อวัดแถว R5 ล่วงหน้าได้ก่อนมีสาย
จริง — ตัวเลขจากสายสมมตินี้ **ไม่ใช่ตัวเลขของสายจริง** และหัวรายงานจะเตือนไว้ทุกครั้งที่ใช้

อ่านตารางนี้ต้องระวังสองเรื่องก่อน: (ก) คอลัมน์ "still missing at spark" วัดที่ 150 ครั้งฝั่งเรา
แต่ 180 ครั้งฝั่ง GenshinLike (Genshin ไม่มี spark จริง 180 คือกรณีแย่สุดจนได้ตัวชูโรงแน่นอน)
(ข) **พูลของเราเล็กมาก** — R4 มี 2 สาย ส่วนชั้น 4★ ของ Genshin มีตัวละครกับอาวุธหลายสิบชิ้น
เอาอัตรา 5.1% มาใส่พูล 2 สายตรง ๆ จึงได้ R4 ตัวแรกใน ~8 ครั้ง และตัวซ้ำ R4 สูงถึง 94–99%
ซึ่ง **ไม่ใช่สิ่งที่ Genshin ให้ผู้เล่นรู้สึก** ลอกอัตรามาทั้งชุดจึงผิด

สิ่งที่ตัวเลขบอกจริง ๆ และควรเอามาใช้ (**ข้อเสนอ — ยังไม่ได้แก้ `SummonRules.Proposed`
รอเจ้าของโปรเจกต์ตัดสิน**):

1. **R5 ของเราไม่มีการันตีของตัวเอง** — pity ของเราการันตี "R4 ขึ้นไป" และ R5 ได้แค่ 1 ใน 4
   ของก้อนนั้น ผลคือเมื่อมี R5 จริง 16% ของผู้เล่นยังไม่ได้ตอนถึง spark ส่วนโครง Genshin ที่มี
   pity แยกของชั้นบนสุด (hard 90) ทำให้เหลือ 0% **ควรเพิ่ม pity แยกของ R5** พร้อมกับสาย R5 แรก
   และคง pity R4+ ที่ 60 ไว้
2. **อัตราที่ผู้เล่นรู้สึกคืออัตราต่อสาย ไม่ใช่ต่อชั้น** — แผนทยอยปล่อยจะทำให้พูลโตขึ้นเรื่อย ๆ
   และโอกาสได้สายที่อยากได้ลดลงทุกครั้งที่เพิ่มสาย Genshin แก้ด้วยตัวชูโรง (rate-up 50/50 +
   การันตีรอบถัดไป) **เมื่อเริ่มทยอยปล่อยสาย ต้องมี banner ตัวชูโรงหนึ่งใบ** ซึ่งตรงกับที่
   เอกสารนี้ตั้งไว้แล้ว ("Banner ใบเดียวที่มีตัวชูโรงหมุนเวียน")
3. **Attune ขึ้นกับอัตราของชั้นมาก** — เต็มเพดาน R4 ใช้ ~3,200 ครั้งในโครงของเรา แต่ ~960 ครั้ง
   เมื่อ R4 ออกบ่อยแบบ GenshinLike ควรพิจารณาอัตรา Echo shard ใหม่ตอนล็อกอัตรา ไม่ใช่ตอนนี้

## สิ่งที่ตั้งใจตัดออก

- **ระบบสุ่มไอเทม/อุปกรณ์** — มีแค่สุ่มตัวละครอย่างเดียว เพิ่มชั้นความสุ่มที่สองทับกัน
  คือวิธีที่เกมแนวนี้กลายเป็นเกมที่เล่นแล้วเหนื่อย
- **Banner หลายใบพร้อมกัน** — เริ่มจากใบเดียวที่มีตัวชูโรงหมุนเวียน
- **สุ่มแล้วได้สแตทสุ่ม** — สแตทมาจาก `Progression.ComputeStats()` ซึ่งเป็นฟังก์ชันบริสุทธิ์
  ไม่มี RNG การซ้อนความสุ่มสองชั้นทำให้ preview ที่ตรงกับผลจริงเป็นไปไม่ได้ ซึ่งขัดกับเหตุผล
  ที่หลังบ้านเป็น C# ตั้งแต่แรก
- **การแลกเปลี่ยนตัวละครระหว่างผู้เล่น** — ยังไม่ทำในเวอร์ชันแรกตาม
  [00-overview.md](00-overview.md) แต่ `OwnedCharacter.InstanceId` ออกแบบไว้รองรับแล้ว

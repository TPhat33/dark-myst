# ตัวละครและระบบ evolve

ระบบนี้คือที่ที่เวลาของผู้เล่นถูกใช้ไปจริง ๆ กฎทุกข้อจึงถูกล็อกก่อนเริ่มเขียนระบบ
และมีเทสต์รองรับใน `tests/DarkMyst.Content.Tests/EvolutionTests.cs`

## ตัวละครแต่ละตัวเป็นข้อมูลเฉพาะตัว

| ข้อมูล | เก็บที่ |
| --- | --- |
| ต้นแบบตัวละคร (สาย, สกิลพื้นฐาน, ชุดภาพ) | `content/characters.json` |
| ตัวละครที่ผู้เล่นครอบครอง (รหัสเฉพาะ, เจ้าของ, เวลาที่ได้) | `OwnedCharacter` |
| พัฒนาการ (เลเวล, ร่าง evolve) | `OwnedCharacter.Level` / `.CharacterId` |
| ผลจากการปั้น (สแตทที่สืบทอด, แนวทางเน้น) | `.InheritedBonusPerMille` / `.Focus` |
| ประวัติ evolve (ใช้ตัวใด สูตรเวอร์ชันใด) | ตาราง `evolve_history` ฝั่งเซิร์ฟเวอร์ (ระยะ D) |
| สถานะป้องกันความผิดพลาด | `.IsLocked` / `.IsInUse` |

`InstanceId` **ไม่เคยถูกใช้ซ้ำ** แม้ตัวละครจะถูกใช้เป็นวัตถุดิบไปแล้ว
ประวัติจึงชี้กลับไปยังตัวที่หายไปได้เสมอ — และเปิดทางให้ระบบแลกเปลี่ยนในอนาคตโดยไม่ต้องรื้อข้อมูล

## สูตรสแตท

```
stat(level) = base + growth × (level − 1)
final       = stat(level) × (1000 + inherited + focus) / 1000
```

`inherited` และ `focus` ถูกบวกรวมกันก่อนคูณครั้งเดียว ลำดับจึงไม่มีผล

| ขั้น | เพดานเลเวล |
| --- | --- |
| I | 20 |
| II | 40 |
| III | 60 |

## คำตอบของห้าคำถามที่ต้องล็อกก่อนเขียนโค้ด

### 1. ใช้กี่ตัวเพื่อ evolve แต่ละขั้น

| จาก | ต้องถึงเลเวล | วัตถุดิบ | ต้องเป็นสายเดียวกัน | ทอง | ไอเทม |
| --- | --- | --- | --- | --- | --- |
| I → II | 20 | 2 ตัว | 0 | 5,000 | ตรา 3 |
| II → III | 40 | 3 ตัว | 1 | 25,000 | ตรา 8 + แก่น 2 |

### 2. สแตทส่วนใดสืบทอดและมีเพดานอย่างไร

วัตถุดิบแต่ละตัวให้ **essence**:

```
essence = level × 10 + (rarity − 1) × 50 + evolveStage × 100
```

แล้วคูณด้วยสัดส่วนตามความใกล้ชิด:

| ความสัมพันธ์กับตัวที่ปั้น | สัดส่วน | โบนัส |
| --- | --- | --- |
| สายเดียวกัน | 100% | +20 essence |
| ธาตุเดียวกัน (คนละสาย) | 50% | — |
| ไม่เกี่ยวข้องกัน | 0% | — |

`inherited` ที่ได้ = `essence รวม / 10` per-mille **สะสมตลอดชีวิตของตัวละคร
และตัดเพดานที่ 300 per-mille (+30%)**

สืบทอดเฉพาะ `MaxHp`, `Attack`, `Magic`, `Defense`, `Resist`
**`Speed`, `CritRate` และ `CritDamage` ไม่สืบทอด** โดยตั้งใจ — ลำดับความเร็วต้องยังเป็น
เครื่องมือออกแบบที่คาดเดาได้ ไม่ใช่ผลพลอยได้ของว่าใครฟาร์มมากกว่ากัน

### 3. ของซ้ำมีทางทดแทนหรือไม่

มี นี่คือเหตุผลที่สัดส่วนถูกแบ่งเป็นสามระดับ ผู้เล่นที่ไม่เคยได้ตัวซ้ำเลย
ยังไปถึงเพดานได้ด้วยวัตถุดิบธาตุเดียวกัน แค่ช้ากว่าเท่าตัว

ขั้น II → III บังคับสายเดียวกันอย่างน้อย 1 ตัว — ร่างสุดท้ายจึงยังเป็นเป้าหมายที่ต้องตั้งใจ

### 4. แนวทางเน้นสแตท (focus) และการแก้การปั้นพลาด

เลือกหนึ่งอย่างตอน evolve:

| Focus | ได้ | เสีย |
| --- | --- | --- |
| Offense | Attack +12%, CritDamage +6% | Defense −6% |
| Guard | MaxHp +12%, Defense +8% | Speed −6% |
| Swift | Speed +10%, CritRate +25% | MaxHp −8% |
| Arcane | Magic +12%, Resist +6% | Attack −6% |

การแก้: ไอเทมพรีเมียม *Reforge Stone* รีเซ็ต **focus อย่างเดียว** โดยคงเลเวล ขั้น
และสแตทที่สืบทอดไว้ ไม่มีวิธีคืนวัตถุดิบที่ใช้ไปแล้ว — และหน้าจอยืนยันต้องบอกเรื่องนี้ชัดเจน

### 5. การปรับสมดุลในอนาคตมีผลกับตัวที่ปั้นไปแล้วอย่างไร

สแตทไม่ได้ถูกเก็บเป็นตัวเลข แต่ **คำนวณใหม่ทุกครั้งจากสูตร** โดยอ้างอิง content version
ที่ปักไว้บนตัวละคร (`OwnedCharacter.ContentVersion`)

การปรับสมดุลจึงเป็นการออก content version ใหม่ และ **การย้ายตัวละครไปเวอร์ชันใหม่
เป็นขั้นตอนที่ตั้งใจทำและบันทึกไว้ ไม่ใช่สิ่งที่เกิดขึ้นเงียบ ๆ** นโยบายที่ต้องประกาศล่วงหน้า:

- ตัวละครที่ถูกลดพลัง: ผู้เล่นได้สิทธิ์คืนวัตถุดิบเต็มจำนวนภายในหน้าต่างเวลาที่กำหนด
- ตัวละครที่ถูกเพิ่มพลัง: มีผลทันทีกับทุกตัว
- การสำรวจที่กำลังเล่นค้างอยู่ **ใช้เวอร์ชันเดิมจนจบรอบ** ผู้เล่นจะไม่เจอสูตรหรือบอสเปลี่ยนกลางทาง

## ลำดับที่เซิร์ฟเวอร์ต้องทำทุกครั้งที่ evolve

1. ตรวจว่าผู้เล่นเป็นเจ้าของตัวละครและวัตถุดิบจริง
2. ตรวจว่าตัวละครไม่ได้ถูกใช้งานหรือถูกล็อก
3. คำนวณผลด้วย `Evolution.Preview()` — ฟังก์ชันเดียวกับที่ไคลเอนต์ใช้แสดง preview
4. หักวัตถุดิบ ทอง ไอเทม และบันทึกตัวใหม่ **ในธุรกรรมเดียว**
5. บันทึกประวัติ และป้องกันคำขอซ้ำจากการกดซ้ำหรือเน็ตหลุด (idempotency key)

`Evolution.Preview()` เป็นฟังก์ชันบริสุทธิ์ ไม่เขียนอะไรเลย เซิร์ฟเวอร์เรียกสองครั้ง —
ครั้งแรกเพื่อวาดหน้าจอยืนยัน ครั้งที่สอง **ภายในธุรกรรม** ที่หักวัตถุดิบจริง
ไคลเอนต์ที่ถือข้อมูลเก่าจึงหลอกให้ได้ผลที่ข้อมูลปัจจุบันไม่รองรับไม่ได้

ถ้าข้อมูลเปลี่ยนไประหว่างนั้น ต้องแสดงผลใหม่ให้ผู้เล่นเห็นก่อน ไม่ใช่ทำต่อเงียบ ๆ

## รายการที่เซิร์ฟเวอร์ต้องปฏิเสธ

ทุกข้อมีเทสต์:

- ตัวละครยังไม่ถึงเลเวลที่กำหนด
- จำนวนวัตถุดิบไม่ตรงเป๊ะ
- ตัวละครหรือวัตถุดิบถูกล็อก
- วัตถุดิบอยู่ในทีมหรือกำลังสำรวจอยู่
- ใช้ตัวเองเป็นวัตถุดิบ
- ส่งวัตถุดิบตัวเดียวกันซ้ำ
- วัตถุดิบเป็นของผู้เล่นคนอื่น
- ตัวละครอยู่ร่างสุดท้ายแล้ว
- ขั้น II → III โดยไม่มีวัตถุดิบสายเดียวกัน

## หน้าจอ preview

ต้องแสดงก่อนยืนยันเสมอ: สแตทก่อน/หลัง, essence ที่ได้, โบนัสสะสมใหม่ (และบอกเมื่อชนเพดาน),
ค่าใช้จ่าย, และรายชื่อวัตถุดิบที่จะหายไป

`EvolvePreview.StatsAfter` ต้องเท่ากับ `Progression.ComputeStats(preview.Result)` เสมอ —
มีเทสต์บังคับไว้ เพราะ preview ที่ไม่ตรงผลจริงคือสิ่งที่ทำลายความเชื่อมั่นเร็วที่สุด

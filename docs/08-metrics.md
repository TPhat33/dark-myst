# ตัวชี้วัด

อย่าวัดเพียงยอดเล่นหรือยอดเติม ควรเก็บเหตุการณ์ที่ **ตอบคำถามด้านการออกแบบ** ได้

## คำถามที่ต้องตอบได้

| คำถาม | เหตุการณ์ที่ต้องเก็บ |
| --- | --- |
| ผู้เล่นผ่านการจัดทีมและการต่อสู้ครั้งแรกหรือไม่ | `tutorial_team_confirmed`, `tutorial_battle_finished` |
| ใช้เวลานานเท่าไรถึงได้ตัวละครที่ตั้งเป้าและ evolve ครั้งแรก | `character_obtained`, `evolve_completed` (พร้อมเวลาเล่นสะสม) |
| ปรับทีมหลังแพ้ หรือออกจากเกมทันที | `battle_lost` → `team_changed` \| `session_ended` |
| มีตัวละครและแนวปั้นกี่แบบที่ถูกใช้งานจริง | `team_confirmed` (รายชื่อตัวละคร + focus ของแต่ละตัว) |
| แชร์ทีมและกลับมาปรับทีมตามคำแนะนำหรือไม่ | `team_shared`, `team_imported`, `team_changed` |
| คนฟรี คนดูโฆษณา และคนเติม ก้าวหน้าต่างกันเท่าไร | จัดกลุ่มผู้เล่นแล้วเทียบเส้นความก้าวหน้าเดียวกัน |
| ผู้เล่นกลับมาวันที่ 1, 7, 30 มากน้อยแค่ไหน | retention แยกตามกลุ่มข้างต้น |
| รายได้หลังค่าธรรมเนียมคุ้มต้นทุนหรือไม่ | รายได้สุทธิ เทียบ ค่าดูแลระบบ + ค่าเนื้อหา + ค่าหาผู้เล่น |

## หลักการเก็บข้อมูล

1. **เก็บเหตุการณ์ อย่าเก็บตัวเลขสรุป** — คำถามใหม่จะเกิดขึ้นเสมอ และข้อมูลดิบตอบได้
   ส่วนตัวเลขสรุปที่คำนวณไว้ล่วงหน้าตอบไม่ได้
2. **ติด `contentVersion` และ `rulesVersion` ไปกับทุกเหตุการณ์** ไม่งั้นเทียบก่อน/หลัง
   ปรับสมดุลไม่ได้เลย
3. **เหตุการณ์ที่เกี่ยวกับรางวัลต้องบันทึกฝั่งเซิร์ฟเวอร์** ไคลเอนต์รายงานได้เฉพาะ
   พฤติกรรมที่ไม่มีมูลค่า
4. **ไม่เก็บข้อมูลส่วนบุคคลเกินจำเป็น** และต้องลบได้จริงเมื่อผู้เล่นขอลบบัญชี —
   เป็นข้อกำหนดของ store ด้วย

## ตัวชี้วัดของระยะ C โดยเฉพาะ

เกณฑ์ผ่านของ vertical slice คือ *"เล่นครบวงจรแล้วอยากกลับมาปั้นต่อ"* ซึ่งวัดได้จาก:

- สัดส่วนผู้ทดสอบที่กลับมาเล่นรอบสองภายใน 24 ชั่วโมง โดยไม่มีใครเตือน
- จำนวนผู้ทดสอบที่พูดชื่อตัวละครตัวใดตัวหนึ่งออกมาเองในการสัมภาษณ์หลังเล่น
- สัดส่วนที่ evolve สำเร็จอย่างน้อยหนึ่งครั้งภายในเซสชันแรก

ข้อที่สองไม่ใช่ตัวเลขจากระบบ แต่เป็นสัญญาณที่ตรงกับจุดขาย "ตัวละครที่น่าจดจำ" มากที่สุด
